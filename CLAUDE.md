# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Gains" — a workout-journal SPA. Not a fitness tracker: the product intent (`docs/workout-journal-build-spec.md`) is a digital notebook you carry to the gym — record with minimum friction, voice-first input, no chatbot/assistant framing. That doc is the product/UX source of truth (screen-by-screen specs, design system, section numbers like "§07" that the dev check screens reference); this file is the technical/architecture counterpart — how the thing is actually built, and the non-obvious traps already hit while building it.

## Commands

```
npm run dev       # vite dev server (see "Dev server port" gotcha below)
npm run build     # tsc -b && vite build — the closest thing to a test suite; run this after any change
npm run lint      # oxlint
npm run format    # prettier --write .
npm run preview   # serve the production build locally
```

There is no test framework in this project (no test script, no test runner dependency). `npm run build` (type-check) and `npm run lint` are what stand in for verification — always run both after a change.

`node scripts/verify-rls.mjs` — one-off manual RLs check (creates two throwaway email/password accounts via `+tag` addressing on `RLS_TEST_EMAIL_BASE`, since Google OAuth can't be scripted, and confirms user B can't see user A's session). Requires "Confirm email" off in Supabase Auth settings and `RLS_TEST_EMAIL_BASE` in `.env.local`. Not run automatically anywhere.

## Database / schema workflow

**Not migration-based.** There is no `supabase/migrations/` folder and no Supabase CLI deploy step. `supabase/schema.sql` and `supabase/seed_*.sql` are hand-maintained, idempotent SQL files (`create table if not exists`, `alter table ... add column if not exists`, `drop policy if exists` + recreate, `where not exists (...)` guards on inserts) applied by pasting into the Supabase Dashboard SQL Editor — see `supabase/README.md` for the exact setup sequence. When you change the schema, edit `schema.sql` in place (keep it re-runnable) rather than writing a new migration file, and tell the user which file(s) to paste into the SQL editor.

Key tables (`supabase/schema.sql`):
- `exercise_definitions` — shared reference table, no `user_id`, RLS read-only to all authenticated users. The client never writes to it; it's admin-curated via the SQL editor (`seed_exercises.sql`, `seed_exercise_images.sql`, `seed_exercise_descriptions.sql`). Has `placeholder_image_url`/`placeholder_image_url_peak` (RepDB illustration URLs) and `description` (how-to + "Targets: ..." muscle blurb, one string split client-side by `src/lib/exerciseInfo.ts`'s `splitDescription` on the literal `' Targets:'`).
- `workout_sessions` / `exercises` / `sets` — fully user-owned, RLS via `user_id = auth.uid()`.
- `templates` / `template_exercises` — split model: rows with `is_default = true` have `user_id = null` and are readable by everyone but writable by no one from the client (four separate RLS policies — select allows `user_id = auth.uid() OR is_default`, insert/update/delete require ownership and `NOT is_default`); custom templates are fully owner-controlled. Don't collapse this back into a single "for all" policy.

Exercise image/description attribution: RepDB's free-tier license requires the "Exercise data by RepDB (repdb.co)" credit link, which lives in `src/screens/Me.tsx`'s footer — don't remove it if `placeholder_image_url`/`description` data is still in use.

## Architecture

**Stack:** Vite + React 19 + TypeScript SPA (not Next.js), Tailwind v4 (`@tailwindcss/vite`, tokens defined in `src/index.css`'s `@theme` block, not `tailwind.config.js`), Supabase (Postgres + Auth + RLS) as the only backend, `zustand` for the one piece of client state that needs it (`src/store/authStore.ts`), `react-router-dom`, `roughjs` for the hand-drawn visual style, `vite-plugin-pwa`. Deployed to Vercel as a static SPA (`vercel.json` is just SPA rewrites + no-cache headers on `sw.js`/`manifest.webmanifest`/`index.html`).

**No data layer / no generated types.** There's no `database.types.ts`, no React Query/SWR, no repository/service layer. Every screen that needs data does its own `useEffect` + `useState` + inline `supabase.from(...).select(...)` call, and defines its own local TypeScript types shaped to match that specific `select()` (e.g. `TemplateDetails.tsx` and `ActiveSession.tsx` each have their own `ExerciseDefinition` type covering only the columns they select). When you widen a query, you widen its local type in the same file — there's no central type to update. This is a real convention, not an oversight; follow it rather than introducing a shared data layer.

**Auth:** Google OAuth only (no email/password UI — email/password exists solely for `verify-rls.mjs`'s scripted test accounts). `src/store/authStore.ts` holds `user`/`session`/`loading` and subscribes to `supabase.auth.onAuthStateChange`. `src/components/RequireAuth.tsx` wraps individual routes in `App.tsx`; `/me` is deliberately *not* wrapped (it renders its own signed-out state). `signInWithGoogle` explicitly passes `redirectTo: window.location.origin` — but Supabase only honors that if the exact origin is in the dashboard's Authentication → URL Configuration → Redirect URLs allowlist, otherwise it silently falls back to the configured Site URL (which can be the Vercel prod URL, not localhost). Combined with `vite.config.ts` not pinning a dev server port, running multiple `npm run dev` instances concurrently drifts across ports (5173 → 5174 → 5175...) and each new port needs its own allowlist entry — this has already caused "login redirects me to the Vercel app" confusion once.

**Design system — the "Sketchy" hand-drawn look is load-bearing, not decorative:**
- `src/components/Sketchy.tsx` wraps `roughjs` to render a wobbly rounded-rect (or ellipse/line) border and/or fill as absolutely-positioned SVG paths sized from explicit `width`/`height` props (it does not measure itself). Every bordered/filled shape in the app (`Card`, `Button`, `IconButton`, `Modal`, `NotesBox`, the activity-graph squares, ...) gets its shape from this component, not CSS `border`/`background`.
- Sizing pattern: a component measures its own rendered size via `src/lib/useMeasure.ts` (a callback-ref + `ResizeObserver`, chosen specifically because plain `useRef` + layout-effect misses elements that mount later, e.g. a conditionally-rendered `Modal`) and feeds that into `Sketchy`. **Known failure mode:** if `Sketchy` is the *only* thing providing a background and the measurement lags a content reflow (web font swap, async content), the container can render fully transparent for a frame — this bit `Modal.tsx` in production use; the fix there was adding a plain CSS `bg-paper` background as a synchronous fallback underneath the decorative `Sketchy` layer. Prefer measuring once at a container level and deriving fixed child sizes over giving many small children (e.g. a grid of squares) their own individual `useMeasure`/`ResizeObserver` — both for performance and to avoid repeating this race.
- "Crayon fill" pattern for colored chips/icons/squares: `fillStyle="hachure"` with `hachureGap={2.2}` `fillWeight={2}`, `showStroke={false}` when you want color with no outline. rough.js represents a hachure fill as scribble-line paths where **the color lives in each path's `stroke`, not `fill`** — `Sketchy.tsx` already handles this correctly; don't hand-roll rough.js SVG output elsewhere without accounting for it (see commit "Fix invisible crayon fill").
- Colors are CSS custom properties in `src/index.css`'s `@theme` block (`--color-paper`, `-ink`, `-graphite`, `-sage`, `-sky`, `-sun`, `-coral`, `-lavender`, `-highlight`, `-mist`, `-gold`, `-forest`) — Tailwind v4 auto-generates `bg-*`/`text-*` utilities from these, so add new colors there rather than hardcoding hex in components (the one deliberate exception is `IconButton.tsx`'s hardcoded pressed-state hex per tone, which is a manually-darkened variant of the resting color and must be updated by hand if that base token changes).
- Two Google Fonts, both cursive/handwritten: `--font-display` (Shantell Sans, bold) is applied globally to every `h1`/`h2`/`h3` via a plain CSS selector in `index.css` — it's reserved for actual page headers and section headers. `--font-body` (Covered By Your Grace) is the `body` default. **Don't use `h1`/`h2`/`h3` for per-item labels** (an exercise name in a card, a list-row title) — that was a real bug (session-history exercise names were literal `<h3>`s and rendered in the wrong, too-heavy font); use `<p>` or a `<button>` instead, matching `ExerciseBlock.tsx`'s title button and `TemplateExerciseRow.tsx`.

**Dev check screens** (`src/screens/dev/*Check.tsx`, routed at flat unauthenticated `/_dev/*` paths registered individually in `App.tsx`, outside `RequireAuth`/`Layout`): the established way to build and visually verify a new component in isolation with mock data before wiring it to real data/screens. Each follows the same tiny template (`<div className="mx-auto max-w-[480px] ... bg-paper p-6"><h1 className="... text-2xl font-bold">Label (§NN)</h1>...</div>`), where `§NN` is the next unused section number matching `docs/workout-journal-build-spec.md`. `KitchenSink.tsx` (`/_dev/components`) is a separate, parallel "every component on one page" aggregate — not an index that links to the others — so a new component typically gets added to *both*. When asked to prototype something before it's wired to real data, this is the pattern to follow, not a throwaway scratch file.

**Date handling:** `src/lib/date.ts` (`daysInMonth`, `firstWeekdayOfMonth`, `addMonths`, `toISODate`, `formatMonthYear`) is the only shared date utility module and is local-timezone-safe by design (no `Date#toISOString()`, which converts to UTC and can roll the calendar date over by one depending on the user's offset). Older code predates this and still has the footgun (`isoDateDaysAgo` in `HistoryList.tsx`, `todayKey` in `dailyMotivation.ts`, both do `new Date().toISOString().slice(0,10)`) — it hasn't been retrofitted. Prefer `date.ts` for anything new; `workout_sessions.date` is a plain Postgres `date` column serialized as a bare `YYYY-MM-DD` string, so code that only reads/compares it (not displays it) can often skip `Date` parsing entirely and treat it as an opaque string.

**Voice input:** `src/lib/useSpeechRecognition.ts` (browser `SpeechRecognition` API, has a watchdog/stale-instance-cleanup for hung sessions) feeds `src/lib/voiceParser.ts`, which parses commands like "bench press eighty for eight" into exercise + weight + reps and fuzzy-matches the exercise name against `exercise_definitions` (name + aliases). No exercise selected → no silent fallback guess; it surfaces a clear error instead (this was itself a bugfix — a "for"/"four" homophone collision used to corrupt weight/reps while still matching the exercise name).

**PWA / service worker:** `vite-plugin-pwa` with `registerType: 'autoUpdate'`. A stale service worker can keep serving a cached old JS bundle even against a fresh `npm run dev` on the same origin — if a code change "isn't showing up" in the browser despite `curl`-ing the dev server and confirming the new source is served, suspect the service worker/browser cache before the code. The project already added a `controllerchange` listener as a more reliable update trigger; if that's not enough, the fix is on the browser side (unregister the SW / hard reload), not the code.
